# The workload catalog

Generated by `aeiou-catalog write` from the records under `workloads/` (`mechanism.toml`, `case.toml`,
`capture.toml`), the shapes measured from each case's dry run (`shape.json`), and the dictionary
(`attributes.toml`); never edited by hand (`DESIGN_REVIEW.md` §3.66, §3.68). A mechanism is a
directory: an authoring script and its ASTs. A case is an AST and a parameter set; a mechanism
with no case yet shows its abstract at the defaults.

## Coverage

Every category of the dictionary and its classes, with what is in each so far: the tree's
directories, a contribution going in the one whose description fits.

## Glossary

Every attribute and value a record may use (`attributes.toml`). Curated attributes are written in the
records, derived ones read from the AST and the captures, measured ones computed from the dry run.

### `category`

The class of system whose I/O the mechanism reproduces: the tree's first level. *(curated, mechanism, required)*

- `input-pipeline`: The read path that feeds a model its samples: a training job's loader, or batch inference reading a dataset the same way. *Also: training, dataloader, data loading, batch inference.*
- `dataprep`: Preparing data for training: curation, filtering, deduplication, shuffling, packing, tokenization, ingest. *Also: data preparation, etl, curation, preprocessing.*
- `checkpointing`: Saving and restoring a job's state: a training run's, or a simulation's checkpoint and restart. *Also: checkpoint, restore, resume, checkpoint/restart.*
- `model-loading`: Loading a model's weights to serve it: start-up, scale-out, failover, a model swap. *Also: inference, serving, cold start, weights.*
- `kvcache`: An inference engine's KV cache offloaded to storage and loaded back. *Also: kv cache, prefix cache, kv offload, inference.*
- `vector-search`: Nearest-neighbour search over vectors: building an index and searching it, as a library or a vector database does. *Also: vector database, vdb, ann, rag, retrieval, embeddings.*
- `embedding-tables`: Embedding tables larger than memory, looked up by id (recommender models), in training and in serving. *Also: recommender, recsys, dlrm, embeddings, parameter server.*
- `rl`: Reinforcement learning: rollouts and a trainer, the weights pushed between them, replay buffers. *Also: reinforcement learning, rollouts, rlhf.*
- `agentic`: AI agents' own tool I/O: checkouts, builds, scratch file systems of agent sandboxes (an agent's KV cache is kvcache). *Also: agents, sandbox, coding agent.*
- `software-build`: Building software: checkouts, compiles, links, incremental rebuilds. *Also: compile, build, swbuild, ci.*
- `eda`: Electronic design automation: chip design's front-end (many small files) and back-end (large files). *Also: chip design, semiconductor.*
- `vdi`: Virtual desktops: their images at boot, at login, and in steady use. *Also: virtual desktop, boot storm.*
- `media-ingest`: Media and sensor streams written as they arrive: video acquisition, surveillance, instruments. *Also: video, vda, surveillance, streaming write.*
- `database`: Database engines' I/O: data pages and a write-ahead log, a key-value store's compaction. *Also: oltp, wal, key-value store, lsm.*
- `genomics`: Sequencing pipelines: alignment, sorting, variant calling. *Also: bioinformatics, life sciences, sequencing.*
- `hpc`: Scientific simulation and analysis: N-to-N and N-to-1 output, analysis reads (checkpoint and restart are checkpointing). *Also: simulation, scientific computing, mpi-io.*
- `benchmarks`: Benchmarks whose definition is the workload (IO500, SPECstorage): their defined operations, never a trace of an application. *Also: synthetic, io500, spec, mdtest, ior.*

### `class`

The second level, inside a category large enough to need one; each value belongs to one category, and a category with values has no mechanism outside them. *(curated, mechanism)*

- `map`: Map-style: each sample by its id, in a shuffled order without replacement. *(In `input-pipeline`.)* *Also: random access, map-style.*
- `stream`: Streaming: whole shards in a shuffled order, records taken in shard order. *(In `input-pipeline`.)* *Also: iterable, sharded, webdataset.*
- `scan-filter`: Long sequential reads of a raw corpus, a smaller sequential write: language identification, quality filters, PII scrubbing. *(In `dataprep`.)*
- `shuffle`: All-to-all: wide temporary spill, many-to-many reads and writes: global shuffles, repartitioning, exact deduplication by hash. *(In `dataprep`.)*
- `dedup-index`: An index built, then random lookups against it: fuzzy and near-duplicate deduplication. *(In `dataprep`.)* *Also: minhash, lsh.*
- `repack`: Many small files into large shards or back, metadata-heavy on one side: tar and WebDataset packing, frame extraction. *(In `dataprep`.)*
- `tokenize-pack`: Text in, large binary token files and their index out (Megatron-style .bin and .idx). *(In `dataprep`.)* *Also: tokenization.*
- `ingest`: Many writers landing raw data, often as object PUTs: web crawls, sensor dumps. *(In `dataprep`.)* *Also: crawl, landing.*
- `io500`: The IO500 suite: IOR easy and hard, mdtest easy and hard, find. *(In `benchmarks`.)*
- `specstorage`: SPECstorage Solution: its workloads' defined operation mixes (SWBUILD, VDA, EDA, AI_IMAGE, GENOMICS, …). *(In `benchmarks`.)*

### `phase`

When in a system's life the mechanism's I/O happens; several when its cases span them. *(curated, mechanism, required, several values)*

- `training`: A model being trained (its input, its checkpoints).
- `inference`: A model serving requests (its weights loaded, its KV cache, its retrieval). *Also: serving.*
- `indexing`: Building an index offline for later search.
- `preparation`: Preparing data before a job uses it.
- `production`: A non-AI system doing its work (a build, a database, a simulation).

### `domain`

The field the mechanism's applications come from; several when it serves more than one (a filter, in place of a directory per field). *(curated, mechanism, required, several values)*

- `ai`: Machine learning and AI systems. *Also: ml, machine learning, llm.*
- `hpc`: Scientific and technical computing. *Also: scientific.*
- `enterprise`: Business systems: databases, virtual desktops, file serving.
- `media`: Media capture, production, and delivery.
- `life-sciences`: Genomics and other life-science pipelines. *Also: bioinformatics.*
- `software-development`: Building and testing software. *Also: devops, ci.*

### `application`

The library or program whose I/O the mechanism reproduces, as traced. *(curated, mechanism, required)*

- `pytorch-dataloader`: PyTorch's DataLoader with worker processes over a map-style Dataset. *Also: pytorch, torchvision.*
- `numpy`: NumPy's np.load of .npz archives.
- `h5py`: h5py over libhdf5.
- `tf-data`: TensorFlow's tf.data pipeline. *Also: tensorflow.*
- `pyarrow`: Apache Arrow's Parquet reader. *Also: arrow.*
- `torch-dcp`: torch.distributed.checkpoint (DCP), save and load. *Also: fsdp, pytorch.*
- `transformers-safetensors`: Hugging Face from_pretrained over safetensors shards. *Also: hugging face, huggingface.*
- `faiss`: FAISS (Meta).
- `diskann`: DiskANN (Microsoft), through diskannpy.
- `vllm-lmcache`: vLLM with LMCache's storage backends. *Also: vllm, lmcache.*

### `format`

How the data is laid out in files. *(curated, mechanism, required)*

- `file-per-sample`: One file per sample, read whole (JPEG and the like). *Also: jpeg, imagefolder, small files.*
- `npz`: One NumPy .npz archive per sample.
- `hdf5`: HDF5 containers of fixed-size rows.
- `tfrecord`: TFRecord shards of length-prefixed records.
- `parquet`: Parquet shards of row groups.
- `dcp`: DCP shard files (one per rank) and a .metadata file. *Also: distcp.*
- `safetensors`: safetensors shards: a JSON header and the tensors' bytes.
- `faiss-ivf-ondisk`: A FAISS index file and an inverted-lists file mapped whole.
- `diskann-index`: DiskANN's disk index of 4 KiB sectors, its PQ file, and build temporaries.
- `lmcache-chunks`: One file per KV chunk of a fixed number of tokens, named by prefix hash. *Also: kv chunks.*

### `kind`

What a case is for. *(curated, case, required)*

- `example`: An example case: a configuration small enough to trace, showing that the abstract issues the application's calls. Not a job anyone runs as a benchmark.
- `use`: A use case: a configuration describing a real job, valid at the GPU counts it declares.
- `unsettled`: Not yet decided between the two; the case's README says why.

### `modality`

What the job's data is, as its users name it. *(curated, case)*

- `image`: Still images. *Also: vision, cv.*
- `volume`: Dense arrays per sample (scientific volumes, tensors). *Also: scientific, 3d.*
- `text`: Conversations and documents, as tokens. *Also: chat, llm, nlp.*
- `agentic`: An agent's sessions: long contexts reused across many requests. *Also: agents, coding agent.*
- `vectors`: Embedding vectors. *Also: embeddings.*
- `model-state`: A model's weights or a training job's state. *Also: weights, optimizer state.*

### `model-family`

The kind of model the case's job trains or serves, when there is one. *(curated, case)*

- `llm`: A large language model, generating text. *Also: language model, transformer, gpt.*
- `vision`: An image or video model: classification, detection, segmentation. *Also: cnn, resnet, unet.*
- `speech`: A speech or audio model.
- `recommender`: A recommender model with embedding tables. *Also: dlrm.*
- `discriminative`: A model returning typed decisions with their probabilities rather than generated text. *Also: classifier, decision model.*

### `accelerator`

The accelerator a use case's batch and step time are for: its memory sets the batch, and the batch and the accelerator set a step's compute (DESIGN_REVIEW.md §3.78 points 1 and 18). A use case's directory is named for its job and this value (`unet3d-h100`); code reads the record. An example case, traced on a stand-in, names one only if its trace ran on it. *(curated, case, required when `kind` is use)*

- `h100`: NVIDIA H100 (Hopper). *Also: nvidia, hopper, gpu.*

### `api`

The API the abstract declares for its POSIX names (`posix` key; sync when it declares none), the S3 client's when it has object names. Another API is another workload (CLOSED). *(derived, case)*

- `sync`: Blocking system calls, one thread per actor.
- `mmap`: Mapped files: reads are page faults.
- `libaio`: Linux kernel AIO on O_DIRECT descriptors. *Also: aio, o_direct.*
- `posix-aio`: glibc's POSIX AIO.
- `io_uring`: io_uring.

### `writes`

Whether the abstract writes (declares an output namespace). *(derived, case)*

- `yes`: It writes files of its own.
- `no`: It only reads.

### `inputs`

Whether it reads what another run wrote (an `input` namespace). *(derived, case)*

- `yes`: It reads another run's output: a restore, a cold KV reader.
- `no`: It reads datasets and what it wrote itself.

### `status`

What the captures say: the best verdict of `aeiou-trace compare --judge` over the case's captures. *(derived, case)*

- `untraced`: No capture.
- `accepted`: A capture is within the tolerances.
- `not-accepted`: Captured, but rows are outside; each has its recorded reason.
- `nothing-judged`: Captured, but the trace cannot see the data path (a mapped file).

### `run_length_read`

Contiguous bytes read: the byte-weighted median of read run lengths (half the bytes read move in runs at least this long). *(measured, case)*

Stable within ±25 %.

- `large`: 32 MiB or more.
- `medium`: 1 MiB to 32 MiB.
- `small`: 16 KiB to 1 MiB.
- `tiny`: Under 16 KiB.

### `run_length_write`

Contiguous bytes written: the byte-weighted median of write run lengths. *(measured, case)*

Stable within ±25 %.

- `large`: 32 MiB or more.
- `medium`: 1 MiB to 32 MiB.
- `small`: 16 KiB to 1 MiB.
- `tiny`: Under 16 KiB.

### `request_size_read`

The byte-weighted median of read request sizes, as the application asks; a request larger than the file returns short. *(measured, case)*

Stable within ±25 %.

- `large`: 32 MiB or more.
- `medium`: 1 MiB to 32 MiB.
- `small`: 16 KiB to 1 MiB.
- `tiny`: Under 16 KiB.

### `request_size_write`

The byte-weighted median of write request sizes. *(measured, case)*

Stable within ±25 %.

- `large`: 32 MiB or more.
- `medium`: 1 MiB to 32 MiB.
- `small`: 16 KiB to 1 MiB.
- `tiny`: Under 16 KiB.

### `read_share`

Bytes read over bytes moved. *(measured, case)*

Stable within ±0.02.

- `write-only`: No reads.
- `read-only`: No writes.
- `read-mostly`: At least 80 % of the bytes read.
- `mixed`: 20 % to 80 % read.
- `write-mostly`: Under 20 % read.

### `metadata`

Metadata calls (open, close, stat, fstat, readdir, mkdir, rmdir, unlink, rename, ftruncate, fallocate) per data call (read, write). *(measured, case)*

Stable within ±5 % or ±0.005.

- `high`: Two or more per data call.
- `medium`: 0.5 to 2.
- `low`: 0.01 to 0.5.
- `none`: Under one in a hundred data calls.

### `reads_own_writes`

Whether any read follows a write of the same block (read after write). *(measured, case)*

- `yes`: Some reads read back what the run wrote.
- `no`: No read reads what the run wrote.

### `reread`

Bytes read that the instance had read before, over all bytes read (extents, DESIGN_REVIEW.md §3.79). A training job's value is its epoch count's, a parameter. *(measured, case)*

Stable within ±0.02.

- `repeated`: Half the bytes read or more had been read before.
- `some`: 5 % to 50 %.
- `none`: Under 5 %.

### `skew`

The share of the accessed bytes that go to the most accessed 1 % of the bytes (extents, DESIGN_REVIEW.md §3.79). *(measured, case)*

Stable within ±0.02.

- `skewed`: 10 % or more of the accessed bytes on 1 % of the bytes.
- `uniform`: Under 10 %.
