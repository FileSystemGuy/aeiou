## In brief

One engine per actor; `concurrency` request slots; each request continues an earlier conversation or starts one. In the catalog it is `kvcache/lmcache-local-disk`: application `vllm-lmcache`, format `lmcache-chunks`, phase inference, domain ai. Not yet decided between the two; the case's README says why (`agentx`: agentic data, a llm model), its parameters holding at 1 GPU. Traced: a capture is within the tolerances. `sysp` holds 393 samples, stored as chunk objects (1.5 TiB in 50,304 files and 393 directories), looked up by id; sizes always 4.0 GiB (a lognormal clamped to it). `subp` holds 393 samples, stored as chunk objects (1.4 TiB in 45,588 files and 393 directories), looked up by id; sizes always 3.6 GiB (a lognormal clamped to it). It writes the objects of `kv`, each 32 MiB. The one `gpu` actor (one per GPU): 98,827 times: in phase `warm` while `r < warm`, else `serve`,, compute for `draw(think)`; `load` in parallel, each: open, fstat, ioctl TCGETS, lseek, read 32 MiB, close; for each `s` below `⌈(stored − had) / (prefill_step div chunk_tokens)⌉`: compute for `prefill_per_token × min((stored − had − s × (prefill_step div chunk_tokens)) × chunk_tokens, prefill_step)`; for each `k` below `min(stored, had + (s + 1) × (prefill_step div chunk_tokens))`: open for writing, fstat, ioctl TCGETS, lseek, write 32 MiB, close; compute for `decode_per_token × out`. Measured by dry run at 1 GPU (432,060,816 ops: 72,010,136 close, 72,010,136 fstat, 72,010,136 ioctl, 72,010,136 lseek, 72,010,136 open, 70,475,146 read, 1,534,990 write; 2.1 PiB read, 46.8 TiB written): read runs: large (32 MiB); write runs: large (32 MiB); read requests: large (32 MiB); write requests: large (32 MiB); share of bytes read: read-mostly (98%); metadata ops per data op: high (3); reads its own writes: yes; share of bytes read that are re-reads: repeated (98.4%); share of accessed bytes on the most accessed 1% of bytes: uniform (6.25%).
