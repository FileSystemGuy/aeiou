# Workloads

Every committed abstract, with what was learned from the application it stands for: one
directory per I/O mechanism, under its category (`DESIGN_REVIEW.md` §3.66, §3.68).

```
workloads/
  attributes.toml      the dictionary: every attribute a record may use, its meaning and values
  CATALOG.md           generated by aeiou-catalog: the coverage, every mechanism and case, shapes, glossary
  <category>/
    README.md          generated by aeiou-catalog: what belongs here, what is here
    [<class>/]         a second level where a category has one (its README generated as well)
      <mechanism>/
        README.md            what the application does, what storage sees, what its traces taught
        mechanism.toml       its curated attributes (category, class, application, format, phase, domain)
        <ast_name>.py        the authoring script (aeiou-build writes the AST beside it)
        <ast_name>.ast.json  the abstract, generated, never edited by hand
        kit/                 the capture and fitting scripts of the traced application
        params/              test-sized parameter sets: fixtures, not workloads
        shape.defaults.json, DESCRIPTION.defaults.md
                             generated, for a mechanism with no case: its shape and prose at the defaults
        cases/<case>/
          README.md          the load, its kind, the GPU counts its parameters hold at
          case.toml          its curated attributes (kind, modality, model family), GPU counts, length, metrics block, runs
          params.json        the parameter set (writer.params.json and reader.params.json for a pair)
          shape.json         generated: the measured attributes of each run, its op counts, its datasets' projections
          DESCRIPTION.md     generated: the abstract in prose at these parameters, a paragraph and an account
          captures/<capture>/
            capture.toml     where the raw trace is, and the verdict compare --judge gives on each trace
            trace.metrics.json, trace.tolerances.json, logs, fitted.params.json
```

- **A directory is a mechanism, named for what storage sees, never for a use case.** Image
  and audio classification over one file per sample through a map-style loader are one
  mechanism with two cases; a new directory means a new I/O shape. The AST's name is the
  directory's last part with underscores.
- **A case is a workload a user would ask for**: an AST and a parameter set. An *example
  case* is small enough to trace and shows the abstract issues the application's calls; a
  *use case* describes a real job and holds at the GPU counts it declares. Every case so far
  is an example case but `agentx`, left unsettled (its README says why).
- **A capture** is one traced run under its case: the metrics of the `strace`, not the trace
  (the raw traces are scratch captures, not kept), the tolerance file `aeiou-trace compare
  --judge` reads, the application's logs a fit reads, and the parameters fitted to that run
  when they differ from the case's. No file over about 1 MiB.
- **A category is a class of system whose I/O is reproduced**, named in the words storage
  people use for it: a subsystem for AI (`input-pipeline`, `dataprep`, `checkpointing`,
  `model-loading`, `kvcache`, `vector-search`, `embedding-tables`, `rl`, `agentic`), the
  application class elsewhere (`software-build`, `eda`, `vdi`, `media-ingest`, `database`,
  `genomics`, `hpc`), and `benchmarks` for benchmarks whose definition is the workload (IO500,
  SPECstorage), never presented as an application's I/O. Every category has its directory from
  the start, empty or not, so the tree shows what the catalog means to cover and where a
  contribution goes. There is no directory for AI as such: the `domain` attribute says it, and
  `phase` says when (training, inference, indexing, preparation, production); both take several
  values, so a mechanism that serves two phases or fields lives in one place.
- **A class** is a second level, only where a category is large: `map` and `stream` under
  `input-pipeline`, six classes of load shape under `dataprep`, the suite under `benchmarks`.

## What is here

[`CATALOG.md`](CATALOG.md): every case, with its curated, derived, and measured attributes, and
the glossary of the dictionary they are written in. It is generated by **aeiou-catalog**
(`man/aeiou-catalog.1.md`) and checked in CI, never edited by hand.

## Adding one

A new mechanism: a directory under its category (and class, where it has them; the coverage
table of `CATALOG.md` and each category's README say what belongs where), the script,
`aeiou-build --hermetic --twice` on it, a README, and its `mechanism.toml` (with a `[defaults]`
table until it has a case). A new case: `cases/<case>/` with its parameter file, README, and
`case.toml`. A capture: `captures/<capture>/` under the case it was traced as, with a
`capture.toml` holding the verdict `aeiou-trace compare --judge` gives
(`builder/tests/test_trace.py` checks it). Then `aeiou-catalog write --runner
runner/target/release/aeiou` measures the shapes and regenerates `CATALOG.md`, the category and
class READMEs, and every `shape.json` and `DESCRIPTION.md`. An attribute or value not in
`attributes.toml` is refused: add it there first, with its meaning; a new category or class is
a new value there, and `write` makes its directory. CI rebuilds every AST, checks every
parameter file against its abstract, and runs `aeiou-catalog check`.

Traces we may not publish stay out of this tree, pointers to them included.
