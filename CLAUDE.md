# CLAUDE.md

Abstract-driven I/O benchmark runner (Rust + `io-uring` crate + a pure-Rust TCP coordinator for multi-host; no MPI). Released: v0.2.0 (2026-10-16), after the release-candidate review (`RC1_BUG_LOG.md`).

Built for the MLPerf Storage WG, meant to be general: name packages, modules, env vars, CLIs, files, and config keys for the mechanism or the repo (`aeiou`), never for MLPerf (convention in `PROJECT_BRIEF.md` §8: runner binary `aeiou` with subcommands, Python helpers `aeiou-build`, `aeiou-params`, `aeiou-trace`, `aeiou-catalog`, `aeiou-header`, `aeiou-datagen` (deprecated), and, not yet built, `aeiou-verify`, `aeiou-fit`); anything that is WG process (divisions, published hashes, reference parameters) is listed in `PROJECT_BRIEF.md` §8 and says so where it appears. Adding something WG-specific is a conscious, documented decision.

Invariants that must not be broken:
- Exact per-GPU reproducibility. Randomness is positional: keyed on (seed, gpu_id, site, enclosing loop indices). No per-actor draw counters, no shared stateful RNGs, no work distributed based on timing.
- Split work by global GPU id over positions in the Feistel shuffle, never by host rank or by file id. Position is a formula, `g + G·(b·B + j)`, never a counter shared by a GPU's workers. Epochs are `drop_last`.
- Producers are finite: a loader dispatches exactly `steps` batches. The op multiset is fixed before the run starts.
- The workload fingerprint is order-independent (sum of per-op hashes). Issue order within a GPU is timing-dependent and must never be hashed. The fingerprint is the op multiset and does not cover compute (`step_time`); what a use case's results are compared by is its lock's **workload id** (the canonical resolved values, without the submission's required values and the storage-reported numbers), beside the lock's file hash, which answers whether it is the exact file published (decided 2026-10-21/22, `DESIGN_REVIEW.md` §3.78, `PROJECT_BRIEF.md` §6 item 33; built 2026-10-22, `runner/REFERENCE.md` §17). A lock pins its abstract by path under `workloads/` and `ast_sha256`, is generated and never edited, and the runner refuses an abstract whose hash is not its lock's; values only narrow (locked, default, required), and fragments of one layer combine by agreement, never last-one-wins.
- The dataset seed is separate from `--seed` and lives in the dataset definition and the datagen manifest (`.aeiou-dataset.json` per dataset root; `aeiou run` compares the resolved dataset definition, never the whole parameter set or the abstract hash; datasets are read-only (V12); no generated name may begin with `.aeiou` (V13); output namespaces must be empty at start). A namespace declared `input` is read-only (V14) and comes with the `.aeiou-namespace.json` the run that wrote it left at its root; a run never empties an input root. A namespace also declared `same_run` (V15, contract 0.4) is read under names the writing run drew, and a run whose `--seed`, `--gpus`, or common parameters differ from the writer's is refused before the gate. Rank is only the host index that selects a GPU id range, so `--rank-rotate` changes nothing but which host issues which ops.
- Never materialize per-file data structures. Filenames and sizes are computed from patterns.
- Data is reproducible, not self-describing (revised 2026-09-29): the bytes at `(dataset seed, file id, offset)` are a pure function of that tuple with controlled dedupe and compression ratios; no per-block headers, ever, since they force a dedupe ratio of one. The runner does structural checks only (byte counts, short reads, index bytes match the computed layout); content verification is a separate Python tool (`aeiou-verify`, not yet built), never in a scored run. The runner never interprets sample data.
- Consumed datasets are sample spaces: the Feistel shuffle runs over sample ids (`map` access) or shard ids (`stream` access, where `consume` returns file handles), declared per dataset; an `indexed` dataset is looked up by id and never consumed (contract 0.8, `DESIGN_REVIEW.md` §3.72: every dataset declares `access` and a `layout`, `whole`, `chunked`, `compound`, or `array`; a consumed dataset's directories are `{id div D}` or none; contract 0.9, §3.73: a consumed dataset may declare an `inventory`, a file list in its root that a job reads in place of a walk). Container layout (sample → file, unit, column, offset, length) is a formula from the generic framing fields of `format.framing` (`format.layout` from contract 0.2 until 0.8); format reader protocols come from format classes in the Python builder that emit plain POSIX nodes. The Rust runner is format-ignorant; the builder refuses access modes the format class does not support (V9), and the Python writer checks every file against the framing's geometry.
- Random access is the null model, never the model, for data-dependent workloads (VDB, KV cache). Structure storage can exploit (reuse, runs, skew, dependency shape, write-then-read lag) is expressed with positional distributions and `x @ i` (a binding evaluated at an earlier index of its loop; self-reference only at a strictly smaller index), and checked against real traces with `--dry-run --metrics` (`GRAMMAR_OPTIONS.md` §5).
- The application/solution boundary is the interposition test (`PROJECT_BRIEF.md` §5): CLOSED means every system under test sees the same operation sequence, so a run uses the backend the abstract declares (the API of the traced application; `sync` when it declares none; contract 0.3) and a run under any other backend, buffered against direct included, is another workload and is not compared with it (decided 2026-10-01, `DESIGN_REVIEW.md` §3.48); anything an `LD_PRELOAD` shim could do under an unmodified app is solution. The run seed and file order are application-private.
- The abstract is POSIX-shaped and identical for every I/O backend. Backends (`sync`, `sync-direct`, `posix-aio`, `libaio`, `io_uring`, `mmap`, `gds`, `nixl-posix`, `libnfs`) map ops to APIs behind one trait with an issue half and a completion-source half; they never change the op stream or the fingerprint. List and axes in `PROJECT_BRIEF.md` §4.
- Authoring is the Python builder (Option D, decided 2026-09-30); the serde AST is the contract and the only thing the runner executes. The AST stays symbolic: loops are loop nodes, draws are nodes, parameters are references. Python never runs the workload and never reaches the client nodes. Object sizes in a `namespace` are computed from the writes' positional expressions, never observed with `fstat`.
- No MPI in the runner, and no tokio/tonic outside the object engine: the engine (`runner/REFERENCE.md` §16) brings tokio and `object_store` under the cargo feature `object`, its runtime built on the first object call (revised 2026-10-09, `DESIGN_REVIEW.md` §3.65); `object` and `formats` (the container writers of `aeiou datagen`) are default features, so every build, the release's included, reads and writes S3 and every container format (decided 2026-10-16), and `--no-default-features` leaves both out. Cross-host coordination is blocking `std::net` on dedicated threads behind the `Coordinator` trait (`NAPKIN_MATH.md` §8.A, `runner/REFERENCE.md` §6); rank 0 runs the coordinator in-process, and since `--root` and its endpoints (`--endpoint`, a dataset or namespace placed elsewhere) are the shared storage under test only rank 0 empties namespace roots and writes namespace manifests, from the merged report.
